# Интеграционное тестирование методом «сверху вниз»

Лабораторная по курсу «Интеграционное тестирование». Задание было такое: взять проект, протестировать его методом «сверху вниз», то есть начать с верхних модулей (контроллеров) и постепенно подключать нижние — сервисы, хранилища, базу. Потом разобрать, какие ошибки нашлись, и написать, насколько метод вообще помог.

Полный отчёт лежит в [`report/otchet-top-down.md`](report/otchet-top-down.md), то же самое в Word — `report/Otchet-top-down.docx`. Здесь коротко о том, что я делал и как это запустить.

## Какой проект я тестировал

Я взял наш учебный проект с прошлых занятий — два маленьких сервиса на FastAPI:

- **Users API** — хранит пользователей (при старте там уже есть Анна с id=1 и Пётр с id=2);
- **Orders API** — хранит заказы. Когда создаёшь или читаешь заказ, он каждый раз сходит в Users API и подтянет данные пользователя.

Данные лежат в памяти, никакой настоящей базы нет. Код сервисов скопирован сюда как есть, в папки `users_service/` и `orders_service/`, чтобы репозиторий запускался сам по себе.

## Как я применял метод

Самый верхний модуль тут — контроллер Orders API (`orders_service/app/main.py`), потому что клиент общается именно с ним. С него я и начал, а всё, что он вызывает, сначала заменил заглушками. Потом заглушки по одной заменял настоящими модулями и каждый раз гонял тесты заново.

Получилось пять этапов, на каждый свой файл в `tests/`:

1. `test_td1_controller.py` — только контроллер, всё остальное заглушки (авторизация, хранилище заказов, клиент к Users API).
2. `test_td2_auth.py` — подключил настоящую проверку токена.
3. `test_td3_storage.py` — подключил настоящее хранилище заказов.
4. `test_td4_users_client.py` — подключил настоящий HTTP-клиент, но вместо Users API подсунул ненастоящий сервис, который отвечает как мне нужно (404, 500, медленно, не JSON, с лишними полями).
5. `test_td5_full_system.py` — заглушек не осталось, Orders API работает с настоящим Users API.

Все заглушки лежат в `tests/stubs.py`. Самая полезная оказалась `StubUsersClient`: она не только отдаёт пользователя, но и запоминает каждый вызов, так что по ней сразу видно, сколько раз контроллер ходил за пользователем.

## Что нашлось

Если коротко, пять дефектов:

- **TD-D1.** Если у одного заказа пропал пользователь, весь список заказов (`GET /api/v1/orders`) отвечает 404. Нашёл на первом же этапе.
- **TD-D2.** Существующий заказ отвечает 404 «User not found», и по коду ответа не понять, есть заказ или нет. Тоже первый этап.
- **TD-D3.** Если Users API вернёт лишнее поле (или не вернёт нужное), Orders API падает с 500. Это я увидел только благодаря заглушке, настоящий Users API так пока не делает. На четвёртом этапе проверил то же самое по настоящему HTTP — подтвердилось.
- **TD-D4.** Если отправить `Authorization: Basic ...`, сервис отвечает «Missing Authorization header», хотя заголовок есть.
- **TD-D5.** Самое неприятное: после перезапуска Users API номера пользователей начинаются заново, и в старом заказе показываются имя и email уже другого человека. Это нашлось только на последнем этапе.

Ещё заметил, что для списка заказов сервис ходит в Users API отдельно на каждый заказ (даже если пользователь один и тот же), и что `/health` отвечает 200, когда Users API лежит.

Тесты на дефекты я пометил `xfail(strict=True)`, поэтому общий прогон зелёный, но дефекты никуда не делись: `make defects` показывает их как обычные упавшие тесты.

Мой вывод: для этого проекта метод зашёл хорошо. Почти вся логика сидит в контроллере Orders API, и как раз его метод проверяет первым — четыре дефекта из пяти я поймал на первых двух этапах и сразу понимал, где искать. Минус в том, что заглушки пришлось писать почти столько же, сколько самих тестов, а ошибку в самом нижнем модуле (TD-D5) я нашёл только в конце.

## Как запустить у себя

Нужен Python 3.12 или новее и `make` (на macOS и Linux он обычно уже есть).

```bash
git clone <ссылка на этот репозиторий>
cd integration-testing-top-down
make install
make test
```

`make install` создаёт виртуальное окружение `.venv` и ставит зависимости. Запускать сервисы руками не нужно: тесты сами поднимают их на свободных портах.

`make test` прогоняет этапы по порядку. Если какой-то этап упадёт, следующие не запустятся — в этом и смысл метода: нельзя подключать новый модуль, пока не работает то, что уже собрано. Вывод каждого этапа сохраняется в `results/`.

У меня в конце получается так:

```
test_td1_controller: ok — 7 passed, 4 xfailed
test_td2_auth: ok — 6 passed, 1 xfailed
test_td3_storage: ok — 5 passed
test_td4_users_client: ok — 7 passed, 1 xfailed
test_td5_full_system: ok — 3 passed, 2 xfailed
```

Посмотреть найденные дефекты как обычные падения:

```bash
make defects
```

Должно быть `8 failed` — это и есть восемь тестов на пять дефектов.

Если хочется прогнать один этап отдельно:

```bash
.venv/bin/python -m pytest tests/test_td1_controller.py -v
```

## Что где лежит

```
users_service/     Users API
orders_service/    Orders API
tests/
  lab_kit.py       загрузка обоих сервисов в один процесс и запуск на uvicorn
  conftest.py      фикстуры: сервисы, заглушки, очистка данных перед каждым тестом
  stubs.py         заглушки
  test_td1..5_*.py этапы
results/           вывод тестов по этапам
report/            отчёт (.md и .docx)
run_stages.sh      запуск этапов по очереди
```

Один момент, на котором я застрял: в обоих сервисах пакет называется `app`, и если импортировать их в один процесс, второй путается с первым. Поэтому в `lab_kit.py` есть функция `load_service`, которая загружает пакет одного сервиса и убирает его из `sys.modules`, прежде чем грузить второй. А сервисы я запускаю в потоках, а не отдельными процессами, чтобы `monkeypatch` мог подменять модули на заглушки прямо во время работы сервера.
