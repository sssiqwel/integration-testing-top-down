# Отчёт по лабораторной работе

## Интеграционное тестирование методом «сверху вниз»

## Цель работы

Освоить метод интеграционного тестирования «сверху вниз» на примере учебного проекта: начать с верхнего модуля, постепенно подключать нижние модули вместо заглушек, найти дефекты и оценить, насколько хорошо метод помогает их обнаружить.

## Задание

1. Выбрать проект.
2. Применить метод «сверху вниз»: начать с тестирования верхних модулей (контроллеров).
3. Постепенно добавлять нижние модули: сервисы, хранилища, внешние зависимости.
4. Проанализировать найденные проблемы и дефекты, оценить эффективность метода.
5. Подготовить отчёт с ходом тестирования, найденными проблемами и выводами.

## 1. Теоретическая часть

Метод «сверху вниз» (top-down) — это инкрементальный способ интеграционного тестирования. Сначала тестируется самый верхний модуль, тот, к которому обращается пользователь. Все модули, которые он вызывает, на первом шаге заменяются заглушками (stub). Заглушка — это упрощённая замена настоящего модуля, которая возвращает заранее заданные ответы. Потом заглушки по одной заменяются настоящими модулями, и после каждой замены тесты запускаются снова.

Плюсы метода:

- главный сценарий работы и логика верхнего уровня проверяются в самом начале;
- через заглушку легко создать любую ситуацию, в том числе редкую ошибку нижнего модуля;
- если тест упал после подключения модуля, понятно, что проблема в этом модуле или в его связи с верхним.

Минусы метода:

- нужно писать много заглушек, и они должны вести себя похоже на настоящие модули;
- нижние модули проверяются в последнюю очередь, поэтому их дефекты находятся поздно;
- заглушка может вести себя не так, как настоящий модуль, и тогда тест проверяет не то.

## 2. Описание проекта

Я взял учебный проект `user-order-services`, который мы делали раньше на курсе. В нём два сервиса на FastAPI, данные хранятся в памяти.

**Users API** — пользователи:

- `models.py` — модели и проверка данных (имя, email);
- `storage.py` — хранилище в памяти, при запуске есть Анна (id=1) и Пётр (id=2);
- `auth.py` — проверка Bearer-токена;
- `main.py` — эндпоинты.

**Orders API** — заказы:

- `main.py` — контроллер: эндпоинты `/health`, список заказов, заказ по id, создание заказа;
- `auth.py` — проверка токена;
- `models.py` — модели заказа и снимка пользователя;
- `storage.py` — хранилище заказов в памяти;
- `users_client.py` — HTTP-клиент, который запрашивает пользователя в Users API.

### 2.1. Иерархия модулей

Для метода «сверху вниз» важно понять, кто кого вызывает. Клиент обращается к Orders API, поэтому верхний модуль — контроллер Orders API.

```
Orders API: main.py (контроллер)            ← уровень 1, отсюда начинаю
 ├── auth.require_token                      ← уровень 2
 ├── storage.OrderStorage                    ← уровень 2
 └── users_client.get_user                   ← уровень 2
       └── HTTP → Users API                  ← уровень 3
              ├── main.py, auth.py
              └── models.py, storage.py
```

`models.py` в Orders API я не заменял заглушкой: FastAPI использует модели для разбора запроса, без них контроллер не работает.

### 2.2. Порядок подключения модулей

| Этап | Что настоящее | Что заменено заглушкой |
|---|---|---|
| 1 | контроллер Orders API | auth, storage, users_client |
| 2 | + auth | storage, users_client |
| 3 | + storage | users_client |
| 4 | + users_client | Users API (вместо него ненастоящий сервис по HTTP) |
| 5 | + Users API | ничего, полная система |

### 2.3. Заглушки

Заглушки лежат в файле `tests/stubs.py`:

- **заглушка auth** — подмена зависимости FastAPI, пропускает любой запрос;
- **StubOrderStorage** — хранилище, в которое можно заранее положить нужные заказы, и которое запоминает, что в него записали;
- **StubUsersClient** — вместо HTTP-запроса берёт пользователя из словаря, умеет отвечать «пользователь не найден» и «сервис недоступен», записывает каждый вызов;
- **FakeUsersApi** — маленький ненастоящий Users API, который работает по HTTP и отвечает так, как скажет тест: нормально, 404, 500, не JSON, с задержкой, с лишними полями.

## 3. Ход работы

### 3.1. Как устроены тесты

Тесты лежат в папке `tests`, по одному файлу на этап. Оба сервиса загружаются в один процесс и запускаются через uvicorn в отдельных потоках. Запросы идут по настоящему HTTP, а заглушки подставляются через `monkeypatch`. Перед каждым тестом хранилища очищаются.

Users API хранит данные в памяти, поэтому его перезапуск я имитирую сбросом хранилища (`storage.reset()`): остаются только Анна и Пётр, а счётчик id начинается заново, как после рестарта процесса.

Тесты с найденными дефектами помечены `xfail(strict=True)`. Если дефект исправят, тест начнёт проходить, и pytest сообщит об этом как об ошибке, чтобы пометку сняли.

Запуск по этапам:

```bash
make test
```

Скрипт `run_stages.sh` запускает этапы по очереди и сохраняет вывод каждого этапа в `results/`. Если этап упал, следующие не запускаются: нет смысла подключать новый модуль, пока не работает уже собранная часть.

## 4. Найденные дефекты

### TD-D1. Один пропавший пользователь роняет весь список заказов

**Серьёзность:** высокая. **Где найден:** этап 1, подтверждён на этапе 5. **Модуль:** `orders_service/app/main.py`, функции `list_orders` и `enrich_order`.

**Шаги (этап 1):** в заглушку хранилища кладу два заказа: пользователя 1 и пользователя 3. Заглушка users_client пользователя 3 не знает. Запрашиваю `GET /api/v1/orders`.

**Ожидаемый результат:** 200 и список, в котором есть хотя бы заказ пользователя 1.

**Фактический результат:** `404 {"detail": "User 3 not found"}`.

**Причина:** `list_orders` вызывает `enrich_order` для каждого заказа, и первая же ошибка `UserServiceError` превращается в HTTP-ошибку для всего списка.

### TD-D2. Существующий заказ отвечает 404, как будто его нет

**Серьёзность:** высокая. **Где найден:** этап 1. **Модуль:** `main.py`, `get_order` + `enrich_order`.

**Шаги:** в заглушке хранилища есть заказ 1 пользователя 3, заглушка users_client такого пользователя не знает. `GET /api/v1/orders/1`.

**Ожидаемый результат:** ответ, по которому видно, что заказ есть, но пользователь недоступен (например, 200 с сохранённым снимком или 409).

**Фактический результат:** `404 {"detail": "User 3 not found"}`. Клиент по коду 404 решит, что заказа нет.

### TD-D3. Ответ Users API не по контракту даёт 500 в Orders API

**Серьёзность:** средняя. **Где найден:** этап 1 через заглушку, подтверждён на этапе 4 по HTTP. **Модуль:** `main.py` + `models.UserSnapshot`.

**Шаги:** заглушка users_client возвращает пользователя с лишним полем `phone` (или без поля `email`). `POST /api/v1/orders`.

**Ожидаемый результат:** лишнее поле игнорируется и заказ создаётся (201). Если не хватает нужного поля, то 503 «Users API вернул неверный ответ».

**Фактический результат:** `500 Internal Server Error`, обычный текст вместо JSON, без `X-Request-ID`.

**Причина:** у `UserSnapshot` стоит `extra="forbid"`, а ошибку проверки модели в `main.py` никто не ловит. Если в Users API просто добавят новое поле (например, дату регистрации), сломается создание и чтение всех заказов.

### TD-D4. При неверной схеме авторизации сообщение «нет заголовка»

**Серьёзность:** низкая. **Где найден:** этап 2. **Модуль:** `auth.py` (одинаковый в обоих сервисах).

**Шаги:** `POST /api/v1/orders` с заголовком `Authorization: Basic c2VjcmV0`.

**Ожидаемый результат:** 401 с понятным текстом, например «Unsupported authorization scheme».

**Фактический результат:** 401 `Missing Authorization header`, хотя заголовок передан.

**Причина:** `HTTPBearer(auto_error=False)` возвращает `None` для любой схемы кроме Bearer, и код считает, что заголовка нет.

### TD-D5. После рестарта Users API заказ показывает другого человека

**Серьёзность:** критическая. **Где найден:** этап 5. **Модули:** `users_service/app/storage.py` + связь с Orders API.

**Шаги:**

1. Создать пользователя Иван (получил id=3) и заказ «Подарок Ивану».
2. Перезапустить Users API.
3. Создать пользователя Мария — она тоже получает id=3.
4. Запросить заказ Ивана.

**Ожидаемый результат:** id не выдаются повторно, заказ не показывает чужие данные.

**Фактический результат:** в заказе «Подарок Ивану» указаны имя и email Марии.

**Причина:** после рестарта счётчик id в Users API начинается заново, а Orders API хранит только `user_id`. Это утечка персональных данных: один пользователь видит данные другого.

### Наблюдения (не дефекты, но стоит отметить)

- **N+1 запросов.** Заглушка на этапе 1 насчитала 5 вызовов users_client для 5 заказов одного и того же пользователя. Время вызовов складывается: 5 × 1,5 мс = 7,5 мс в заголовке.
- **`/health` не видит зависимость.** На этапе 4 при выключенном Users API заказы отвечают 503, а `/health` отвечает 200.

Четыре дефекта из пяти нашлись на первых двух этапах. Дефекты в логике контроллера нашлись сразу, потому что именно его метод проверяет первым.

### 5.2. Сравнение с «большим взрывом»

В прошлой работе я тестировал этот же проект методом «большого взрыва». Там нашлись те же TD-D1 и TD-D2, но оба давали одинаковый ответ `404 User 3 not found`, и мне пришлось читать код нескольких файлов, чтобы понять, какой модуль виноват.

Здесь на этапе 1 всё, кроме контроллера, было заглушками. Заглушка users_client честно сказала «пользователь 3 не найден», а контроллер сделал из этого 404 на весь список. Значит, ошибка точно в контроллере, искать больше негде.

Кроме того, «сверху вниз» нашёл три дефекта, которых в «большом взрыве» не было:

- TD-D3 — чтобы его увидеть, нужно, чтобы Users API вернул лишнее поле. Настоящий Users API так не делает, а заглушка может;
- TD-D4 — в «большом взрыве» я проверял только «нет токена» и «неверный токен»;
- TD-D5 — нашёлся, когда на этапе 5 я специально проверял, что меняется после рестарта Users API.

### 5.3. Что получилось хорошо

- **Ошибки легко локализовать.** На каждом этапе новым был только один модуль.
- **Легко проверять редкие ситуации.** Через заглушки и FakeUsersApi я проверил 500, ответ не в JSON, таймаут и лишние поля. С настоящим Users API такое почти невозможно воспроизвести.
- **Заглушки считают вызовы.** N+1 запросов я увидел по счётчику вызовов, а не по времени ответа, которое может скакать.

### 5.4. Что было неудобно

- **Заглушки надо писать и поддерживать.** На них ушло примерно столько же кода, сколько на сами тесты.
- **Заглушка может врать.** Например, если бы я сделал в StubUsersClient неправильный текст ошибки, этап 1 проходил бы, а реальная система работала бы по-другому. Поэтому на этапе 4 я повторил проверку TD-D3 по настоящему HTTP.
- **Нижние модули проверяются в последнюю очередь.** Самый опасный дефект (TD-D5) находится в хранилище Users API, которое подключилось только на последнем этапе.

## Вывод

В ходе работы я применил метод «сверху вниз» к проекту Users API + Orders API. Начал с контроллера Orders API, где все нижние модули были заменены заглушками, а потом за пять этапов подключил auth, хранилище заказов, HTTP-клиент и настоящий Users API.

Всего написано 36 тестов: 28 прошли, 8 воспроизводят найденные дефекты. Найдено 5 дефектов (два высокой серьёзности, один критический, один средний, один низкий) и 2 наблюдения.

Метод оказался эффективным для этого проекта. Основная логика проекта находится в контроллере Orders API, и именно её метод проверяет первой, поэтому большинство дефектов нашлось на первом этапе и сразу было понятно, в каком модуле ошибка. По сравнению с «большим взрывом» дефектов найдено больше (5 против 2) и искать их причину было проще. Главный минус — нужно писать заглушки, а дефекты нижних модулей находятся только в конце.

```bash
make install
make test
```

Увидеть дефекты как обычные упавшие тесты:

```bash
make defects
```
